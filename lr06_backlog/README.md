- **Разом:** **18 унікальних історій**. Для кожної є роль, потреба, цінність, щонайменше три перевірювані критерії, клас MoSCoW, бал, ранг, залежності й пропонований реліз.

## 4. Метод пріоритезації

Перший рівень — **MoSCoW** (Must / Should / Could). Другий — прозора зважена оцінка:

`Priority = 4 × Value + 3 × Urgency + 2 × RiskReduction + 1 × Readiness`, де кожна складова **1…5** і вищий бал означає вищий пріоритет. Третій рівень — ID історії при рівності балів. Відтак **ранг — суцільне число 1…18**, унікальне для кожної історії. Ранги відображають цінність і важливість, а **не** порядок технічного виконання: виконання залежить від готовності передумов.

**Value:** користь для користувачів; **Urgency:** критичність для першого релізу; **RiskReduction:** зменшення ризику подвійної броні, втрат, несанкціонованих дій; **Readiness:** зрозумілість вимог та наявність доступів. Конкретні бали — власні аргументовані навчальні оцінки, не позиція реального PO. Деталі: [`prioritization.md`](./prioritization.md).

## 6. Релізний обсяг і реалістичність V06

**Обмеження:** 20 тижнів / 2 тижні = орієнтовно 10 спринтів, по **20 SP** кожний; **200 SP — арифметична верхня планова місткість**, а не оцінена трудомісткість 18 історій і не зобов'язання її заповнити. Суму SP тут **навмисно не придумано**, адже оцінювання власного беклогу передбачено на ЛР8. Після оцінювання BA/Dev/QA та перших фактичних спринтів релізний прогноз переглядається.

**До першого релізу на розгляд:** S-01, S-02, S-03, S-04, S-05, S-06, S-07, S-11, S-12, S-14. **Окрема критична умова:** S-09 (синхронізація розкладу і fail-closed поведінка) — потрібна до **живого** бронювання; якщо власник джерела не підтвердить доступ до контрольної точки W6, допускається **тільки демонстрація на позначених тестових даних, не продуктивний пілот**. Поза базовим MVP: S-08, S-10, S-13. Пропоновані як наступні: S-15, S-16, S-17, S-18. Якщо аудит S-16 буде визначено умовою InfoSec, його треба пересунути до необхідного обсягу, замістивши менш цінний пункт, а не приховано збільшувати реліз.

Детальний умовний план і правило scope trade-off: [`release_plan.md`](./release_plan.md).

## 7. Definition of Ready і Definition of Done

**Ready:** є роль і цінність; погоджені AC; тестові дані; названі залежності й власник їх підтвердження; команда розуміє межу реалізації; після ЛР8 є оцінка SP. Для S-09 додатково потрібне підтвердження доступу до розкладу, інакше `Blocked`.

**Done:** реалізовано і перевірено кожний AC; позитивний і негативний тест; дотримані правила доступу та запобігання конфліктам; додані докази перевірки; QA не має blocker-дефектів; PO прийняв історію. Для інтеграції перевірено актуальність даних та режим збою. **Жоден пункт беклогу не оголошено Done у ЛР6.**

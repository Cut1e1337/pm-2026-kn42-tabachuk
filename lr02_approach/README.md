# ЛР2. Вибір підходу для трьох проєктів

**Студент:** Табачук, КН-42. **Варіант:** V06.  
**Тема семестрового проєкту:** «Сервіс бронювання аудиторій і обладнання з погодженням заявок».

## 1. Три кейси коротко

| Кейс | Обраний підхід | Головний критерій проти | Ціна вибору |
| --- | --- | --- | --- |
| C-1 — звітність до державного реєстру | **Predictive** | `technology` | Менше свободи для реагування на нестабільне API |

## 2. Кейс C-1 — модуль звітності до державного реєстру

**Конфлікт критеріїв.** Формат, контрольні правила і дата звітування визначені регулятором, а приймання й оплата розбиті на три акти. Замовник не бере участі в постійних демо, зміни до fixed-price ТЗ проходять погодження близько двох тижнів. Тому обираю **predictive**: специфікація, контрольні точки, формальна перевірка тестового контуру та приймання після місяця експлуатації. Водночас `technology` тягне до adaptive: новий API частково недокументований, два методи міняли поведінку без попередження, а пісочниця нестабільна.

**Як працювати з критерієм проти.** На початку роблю короткий технічний spike, фіксую перевірену поведінку API та невідомі інтеграційні сценарії у ризик-реєстрі. Для цих сценаріїв запроваджую короткі цикли перевірки у тестовому контурі, але не змінюю нормативну дату та зафіксовані акти. Якщо тестове API недоступне, це явно відображається у статус-звіті й не оголошується успішною інтеграцією.

**Відкинутий варіант — adaptive.** Плюс: можна було б частіше перевіряти реальну поведінку API й міняти пріоритети інтеграції. Мінус: постійна зміна обсягу погано сумісна з тендерним fixed price, двотижневим оформленням змін та замовником, який приймає результат по етапах. **Ціна мого вибору:** додатковий резерв на невизначеність API і повільніші зміни вимог, натомість збереження контрольованого приймання.

**Перший тиждень PM.** Разом з BA створити трасування «поле наказу → перевірка → тест → критерій приймання»; погодити календар актів, критичні дати та правила ескалації. Dev перевіряє два нестабільні методи API й записує результати, QA готує негативні сценарії та тест повторної відправки.

## 3. Кейс C-2 — платіжна частина оренди обладнання

**Конфлікт критеріїв.** Вимоги змінюються після інтерв’ю кожні два тижні, власник продукту відповідає за півгодини, а контракту на зафіксований обсяг немає. Команда працює разом, релізить щотижня і швидко відкочує зміни. Це сильні підстави для **adaptive**. Проти працює `release_cost`: помилка в комісії, заставі чи поверненні може означати реальні неправильні списання та претензії клієнтів.

**Як працювати з критерієм проти.** Не дозволяти, щоб швидкий продуктовий реліз автоматично означав неконтрольований фінансовий реліз. Для платіжних змін виділити правила округлення, інваріанти балансу, тести скасувань і подвійних списань; додати незалежний перегляд PR та контрольоване увімкнення функцій. Гіпотези щодо UX можуть змінюватися щоспринту, фінансові правила — лише після окремої перевірки.

**Відкинутий варіант — predictive.** Плюс: надійніший формальний контроль обсягу платіжного контуру. Мінус: жорстка специфікація всього продукту швидко застаріла б після нових інтерв’ю, а компанія має тільки дев’ять місяців фінансування. **Ціна мого вибору:** постійні витрати на автотести та підтримку, замість прогнозованості повного функціонального плану.

**Перший тиждень PM.** Відокремити платіжні історії від решти беклогу, визначити критичні розрахункові сценарії та умови відкату, домовитися з продактом про щоп’ятничний review і критерії випуску грошових змін.

## 4. Кейс C-3 — заміна системи обліку договорів

**Конфлікт критеріїв.** Правила погодження суперечливі й винятки виявляються тільки на демо; структура старої бази невідома, близько восьмої частини записів має неповні дані. Це вимагає адаптивного уточнення. Але fixed-price контракт, річний бюджет без можливості збільшення, підпис фіндиректора на змінах і щомісячні платежі з великою ціною помилки вимагають формального контролю. Тому обираю **hybrid**: незмінні рамки бюджету, релізу та приймання + короткі цикли аналізу маршрутів і міграції даних.

**Як працювати з критерієм проти.** `contract` є головним конфліктом, бо fixed price робить кожне нове виключення з правил потенційною зміною обсягу. Замість прихованого розширення домовляюся про ліміт обсягу: новий виняток замінює менш пріоритетну функцію або переходить у наступний реліз після затвердження протоколу. Усі зміни фіксуються письмово, а щотижневі демо юристів формують пріоритети, але не автоматично нові зобов’язання підрядника.

**Відкинутий варіант — predictive.** Плюс: зрозумілий бюджет, графік і формальна точка приймання. Мінус: повне ТЗ написали до виявлення юридичних винятків, а якість міграційних даних невідома. **Ціна мого вибору:** більше координації між PM, юридичним і фінансовим відділами та додаткове документування рішень.

**Перший тиждень PM.** Провести воркшоп із трьома юристами та фіндиректором, сформувати карту відомих винятків і затвердити мінімальний реліз. Окремо зробити профілювання старих даних, визначити правила обробки договорів без контрагента та спланувати тестовий перенос до запуску нарахувань.

**Захист найменш очевидного рішення — C-3.**

1. **Чому не чистий predictive, якщо контракт fixed price?** Тому що відомий контракт не робить відомими фактичні маршрути погодження чи структуру старих даних. Повністю закрити аналіз наперед означає закласти невиявлені помилки в ТЗ.
2. **Чому не чистий adaptive, якщо юристи доступні щотижня?** Демонстрації прискорюють з’ясування правил, але не скасовують незмінного річного бюджету та необхідності підпису фіндиректора на змінах.
3. **Що робити з критичною новою вимогою перед релізом?** BA оцінює ризик та необхідність, PM пропонує заміну менш важливої функції чи формальну зміну обсягу; фіндиректор підтверджує рішення, а QA не допускає небезпечні нарахування без тестів.

## 5. Стрес-тест контрактом (конверт)

**Було до конверта:** для C-1 обрано `predictive`, оскільки відомі нормативні вимоги, приймання по актах і фіксований строк переважають невизначеність нового API. Найсильніший контраргумент — `technology`.

**Нова умова:** fixed price замінено на **time and material** з оплатою фактичних годин. Нормативна дата звітності, доступність замовника, склад команди й ціна помилки не змінилися.

**Після конверта:** залишаю базовий **predictive** для регуляторного обсягу і зовнішніх контрольних дат, але розширюю адаптивний спосіб виконання API-інтеграції. Зміна договору знімає формальну двотижневу затримку кожної поправки, але не дає підстав прибрати критичні контрольні точки: помилка все одно спричинить неприйняту звітність. Отже, **назва підходу не змінилася, змінився баланс керування невизначеністю**.

**Що зміниться в роботі PM:**

- **Події:** щотижнева технічна перевірка API, коротке планування наступних інтеграційних експериментів, окрема зустріч щодо відповідності наказу та контрольних дат.
- **Артефакти:** окрім базової специфікації й матриці відповідності з’являються журнал припущень API, timesheet та прогноз витрачених годин і залишкового бюджету.
- **Точка приймання:** зберігаю функціональне приймання в тестовому контурі й після місяця експлуатації; оплата годин за T&M не є доказом якості або приймання результату.
- **Перерозподіл ризику:** ризик перевитрат за невизначене API більшою мірою переходить до замовника, який оплачує фактичний час. PM повинен регулярно показувати прогноз годин і пропонувати обмеження витрат; ризик відповідності регулятору лишається спільною управлінською відповідальністю.

**Два робочі ходи PM, коли fixed price, а вимоги мінливі:**

1. **Фіксований бюджет і обмін обсягу один до одного.** Нові вимоги включати лише замість історій подібної трудомісткості з письмовим підтвердженням. *Ціна:* замовник втрачає частину запланованих можливостей, а BA/PM витрачають час на аналіз пріоритетів.
2. **Короткий оплачуваний етап дослідження до фіксації ТЗ.** До основного fixed-price зобов’язання перевірити API, ризики й мінімальні критерії приймання. *Ціна:* пізніший підпис основного договору і додаткові витрати на discovery, зате менша похибка оцінки.

## 6. Власний семестровий проєкт

**Тема:** сервіс бронювання аудиторій і обладнання з погодженням заявок. **Варіант V06:** PM 50%, BA 100%, Dev 100% + Dev 100%, QA 50%; строк до першого релізу 20 тижнів; орієнтир — 20 SP за двотижневий спринт; бюджетний ліміт 1 440 000 грн.

**Обираю гібридний підхід (Hybrid).** Зовнішній контур має бути передбачуваним: погоджені ролі, правила доступу, дедлайн першого релізу, бюджет, критерії недопущення конфліктних бронювань і контроль приймання. Усередині контуру команда працює **двотижневими ітераціями**: BA уточнює сценарії погодження, Dev реалізують пріоритетні історії, QA перевіряє повні ланцюжки, а PM контролює строк і залежності. Тобто **спринт сам по собі не робить підхід суто adaptive** — формальні ворота приймання та обмеження обсягу лишаються.

**Замовник і доступність.** Робоче припущення (поки немає тексту `lr05_themes_context.md`): замовник — адміністрація закладу освіти; уповноважена особа здатна надавати зворотний зв’язок один раз на два тижні, тоді як відповідальні за аудиторії й обладнання залучаються за потреби. Цю доступність потрібно підтвердити на ЛР5. Якщо замовник доступний рідше, BA документує рішення і PM вводить письмове погодження на контрольних точках, не трактуючи мовчання як згоду.

**Чому саме так і чим відрізняється від кейсів.** На відміну від C-1, у сервісу немає опублікованої незмінної державної специфікації; на відміну від C-2, помилкові перетини аудиторій і погоджень не варто безконтрольно виправляти після релізу. Найближча аналогія — C-3 із неочевидними маршрутами погодження, але нашою перевагою є окремий BA на повну ставку і два розробники; слабке місце — QA лише на 50%.

**Зв'язок із ЛР1 (TSB Bank).** Ризик **R-01** — запуск відразу для всіх корпусів — без пілоту відтворює патерн *big bang* із TSB. Тому перше приймання проводимо на обмеженій групі аудиторій і обладнання, а перехід на всі корпуси залежить від успішного тесту. Ризик **R-02** — формально «готові» неоднозначні правила погодження — закриваємо реєстром відкритих рішень BA. Ризик **R-03** — подвійне бронювання через пізню інтеграцію календаря, обладнання й погодження — закриваємо наскрізними тестами до пілота.

| Елемент роботи | Обране правило для наступних лабораторних |
| --- | --- |
| Довжина ітерації | 2 тижні; орієнтир планування 20 SP на спринт, коригується за реальною velocity |
| Події | Sprint Planning на початку; короткі синхронізації 3 рази на тиждень; Refinement щотижня; Review і Retrospective наприкінці двотижневого спринта |
| Дошка і WIP | `Backlog → Ready → In Progress → Review/QA → Done`; WIP: In Progress ≤ 2, Review/QA ≤ 2; заблоковані задачі позначаємо окремо |
| Definition of Done | Є погоджені acceptance criteria; код пройшов review; тести основного шляху заявки та конфліктних бронювань успішні; QA підтвердив результат; документація оновлена; немає критичних дефектів |
| Точка приймання | На кожному Sprint Review BA і представник замовника приймають інкремент; перед першим релізом окремий Go/No-Go за результатами пілоту на обмежених ресурсах |
| Правила зміни обсягу | До кожного релізного контрольного етапу зміни проходять оцінку BA/PM; нова функція витісняє менш важливу або переноситься після релізу |

**Обмеження ресурсу QA.** QA зайнятий половину часу, тому Dev автоматизують базові перевірки конфлікту бронювань, а QA фокусується на сценаріях погодження, відхилення, повторних заявок і скасувань. Це не замінює перевірки QA, а знижує ризик накопичення задач перед релізом.

## 7. Робочий журнал

- Спочатку для C-1 розглядав hybrid через нестабільне API, але після зіставлення регуляторної дати, fixed price та приймання по актах залишив predictive із коротким технічним spike.
- Для C-2 критерій ціни платіжної помилки змінив уявлення про adaptive: потрібна окрема контрольована процедура фінансового релізу, а не просто щотижневе розгортання.
- Для C-3 жорсткий контракт спочатку схиляв до predictive, проте невідомі маршрути погодження та якість даних переважили на користь hybrid.
- Після відкриття конверта переглянув розподіл ризику витрат між сторонами та ритм технічних перевірок C-1. Фінальний висновок — назву підходу зберегти, але оновити події й артефакти.
